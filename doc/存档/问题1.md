结论分两层：

1. 设计的“帧级卸载能显著释放 CPU”这一核心目标，现有数据强烈支持。
2. 但还不能严谨地宣称“整套设计正式实验成功”，因为满载 S4 的 P99 代理为 34.723 ms，略超 33.333 ms；且性能短跑批未完成逐帧 CRC 等价验证。

CPU 侧的证据很强：帧级卸载相对矩阵卸载，将 active cycles 中位数降低了 97.27%–99.82%。S4 从 1,863,108 cycles 降到 3,405 cycles，说明逐顶点、逐三角形和排序等工作确实已从 CPU 转移到硬件。综合结果也健康：LUT 31.75%、BRAM 23.29%、DSP 5.41%，时序全部满足。

不过，RTOS 空闲率目前不能作为结论证据，它的测量实现有问题，所以三种模式才会都显示约 99.95%–99.98%。

原因在 [rt3d_metrics.c](D:\FPGA\Electrix-3d\sdk\software\examples\rt_3d\rt3d_metrics.c) 中：`rt3d_idle_sample()` 每帧结束都会调用 `idle_account()`；而 `idle_account()` 将“从上次记录到当前”的全部经过周期都累加到 `idle_cycles`。这段时间包含了 CPU 正在执行渲染、MMIO 与调度的周期，并非真正处于 Idle 线程的周期。因此空闲率会被系统性高估到接近 100%。

原始数据也直接说明其不可信：S4 CPU 全软件的 active cycles 已约占该帧 wall cycles 的 82.6%，却仍报告 99.97% 空闲；两者不可能同时代表同一个时间窗的真实 CPU 利用率。相比之下，S4 帧级卸载 active/wall 约为 0.32%，这才与“CPU 负担显著下降”相一致。

建议论文中：

- 保留 active cycles、端到端延迟、资源/时序作为主证据；
- 删除或明确标注 RTOS 空闲率为“当前实现不纳入结论”；
- 将结论写为：S0–S2 支持实时性代理判据；S3/S4 证明 CPU 卸载成功，但满载实时性仍需优化和正式复测；
- 修复 Idle 计数后，再用同一个帧窗口报告真实 idle rate 与后台任务吞吐。

## 推荐修复：以调度切换边界计账

不应在 `rt3d_idle_sample()` 中调用 `idle_account()`，也不应仅在 Idle hook 中以两次 hook 的时间差累加。后者无法知道 Idle 线程何时被抢占，因此下一次进入 Idle 时会把前一段非空闲时间一并计入。

建议启用 `RT_USING_HOOK`，使用 RT-Thread 已有的 `rt_scheduler_sethook(from, to)`：

1. `to == rt_thread_idle_gethandler()` 时记录 `idle_enter_cycle = now`。
2. `from == rt_thread_idle_gethandler()` 时累加 `now - idle_enter_cycle`，然后清除“正在 Idle”状态。
3. 每帧采样只读取累计值并更新采样窗口，绝不把采样点到上次切换点的时间强行计为 idle。
4. 初始化和停止测量时均关闭计账，并使用无符号减法处理 32 位计数器回绕。

这条路径的度量定义明确：仅“调度器确认当前线程为 Idle”的区间会被累计。它需要一次小范围的 RT-Thread hook 配置变更，并应在 S0、S4 各跑至少一次：验证 `0 <= idle_rate_permille <= 1000`、`idle_cycles <= sample_cycles`，且 CPU_ONLY 的 idle rate 明显低于帧级卸载。修复前的 idle rate 只能作为无效数据保留，不得与修复后的结果混合比较。

备选方案是直接报告 `active_cycles / wall_cycles` 与后台吞吐，完全删除 “RTOS idle rate” 指标；这是当前截稿风险最低的做法，但它不提供全系统空闲率。

## 需要与性能问题分开处理的事项

- S4 P99 34.723 ms 超过 33.333 ms：这是实时性余量问题，不是 Idle 计数修复能够解决的问题。优先剖析最长帧的 Scene Controller、DVI/PRESENT 等待和调度开销，再决定降低输入规模、优化流水线或调整目标帧率。
- 性能短跑缺少逐帧 CRC 等价：应以同一 `MODEL`、同一帧窗口、三种模式分别保存 UART JSONL、CRC 与结果 JSON；快速回归可少转储图像，但不能跳过 UART/CRC 验证。
